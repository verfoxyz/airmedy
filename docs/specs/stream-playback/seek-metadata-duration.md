# 最终方案：时长取自元数据，seek 只走「等数据 + 重开解码器」

> 状态：待开工
> 目的：结束字节 seek/回退反复失败；用一条可靠路径解决“不完整文件下拖动无声/切歌”
> 关联：`fix-prefetch-seek-deadlock.md`、`fix-byte-seek-offset.md`、`cache-file-decoder.md`

---

## 1. 结论先行

- **时长不需要完整文件**：源元数据（Last.fm/曲库里就有 `duration`）、FLAC STREAMINFO、MP3 头都能给出时长；
- 因此**不做全文件探测**，所有时长一律用元数据；
- seek 不再尝试“原地字节定位”，统一为：**补数据 → 重开解码器 → 时间戳定位**。

## 2. 现状为什么失败

- 字节 seek 公式/钳制多次出错，落点不对；
- 失败后回退时间戳 seek，在未完成/无索引容器上又失败；
- 失败后解码器从头开始 → 很快触发“播放结束 → 下一首”；
- 日志里 `duration=0` 是**参数没传**，不是拿不到。

## 3. 目标实现（唯一路径）

### 3.1 时长来源（不再依赖解复用器）

- `duration = track.Duration`（秒）；
- 若 `track.Duration <= 0`：从缓存会话/元数据表补；
- 仍为 0 → 显示“无法定位”（不允许把 0 当作有效时长）。

### 3.2 seek 流程

```
Seek(target):
  duration = metadataDuration()
  if duration <= 0: 提示失败，返回
  bytesPerSec = total / duration              // total 可未知时用码率估算
  need = target * bytesPerSec + 1 MiB         // 目标 + 余量
  if received < need:
      通过 demand 标记“需要下载到 need”，并暂停输出（显示缓冲）
      等待 received >= need（超时 30s → 失败提示）
  reopenDecoder(target)                       // 从本地文件重新打开 + 时间戳 seek
  if reopen/seek 失败: 提示失败，播放状态置 paused
```

- **不再原地 seek**（无论已缓存与否）；
- **不再字节 seek**，删除相关分支与回退状态；
- 重开前必须确保 `target + 1MiB` 已落盘，避免解码器在边界等待；
- 重开成功后 `trackStartTime` 按目标位置校正。

### 3.3 防止“seek 失败 → 切歌”

- seek 进行中/失败时，不参与 `HandleTrackEnd` 判定；
- 解码器 EOF 只有在“文件已完成或下载结束”时才视为真实结束；
- 否则视为“数据未到”，暂停并等待 demand 补数据。

### 3.4 与预取/看门狗

- 预取水位保持（demand 期间忽略）；
- 看门狗不因 seek 期间的位置停滞而重载；
- 重开失败最多重试一次，然后明确报错。

## 4. 测试

**Go / C**

- `duration` 来自元数据（不完整文件也能 seek）；
- `duration <= 0` → 提示失败，不崩溃；
- 目标已缓存（`received >= need`）→ 直接重开并成功 seek；
- 目标未缓存 → 进入缓冲，下载到 `need` 后重开成功；
- 重开失败 → 状态 paused + 错误事件，不切歌；
- 下载失败 → 停止等待并提示；
- 回归：完整文件 seek、0s、拖动到结尾、播放结束正常切歌（真实结束时仍切）。

**人工（一次验证）**

1. 5s → 10s：缓冲后有声，位置正确；
2. 5s → 0s：立即有声；
3. 拖到缓存外：显示缓冲，到达后有声；
4. 播放到自然结束：正常切下一首；
5. 下载失败时拖动：提示失败，不切歌。

## 5. 验收

- 拖动不再切歌；
- 不完整文件也能准确定位；
- 只有真实播放结束才切歌。

## 6. 风险

- 每次 seek 都重开解码器，延迟约 100–300ms（可接受）；
- 元数据时长与实际略有偏差（±1–2s），对定位影响小于当前故障；
- 删除字节 seek 后，无索引容器的定位依赖时间戳 seek 的成功率，失败时明确提示而不是静默。
