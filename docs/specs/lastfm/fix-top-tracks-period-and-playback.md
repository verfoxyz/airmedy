# 修复：常听曲目只有 2 首 + 匹配到的源歌曲不可播

> 状态：✅ 已完成（代码已合入 wip/stream-playback）
> 现象：Last.fm 页只显示 2 首；其中「新·与天齐 - 指尖笑」标了网易云，但播放失败
> 范围：MVP 常听曲目的取数范围 + 匹配后的可播性

---

## 1. 只有 2 首：`period=7day` 的数据本来就少

实测（当前账号）：

| period | 返回条数 |
|---|---|
| `7day` | **2** |
| `1month` | 50 |
| `overall` | 50 |

`user.getTopTracks` 的 `7day` 只统计最近 7 天，这个账号只播过 2 首，所以列表只有 2 条——不是解析问题。

### 修法

- 默认改用 **`overall`**（“常听曲目”本来就是全部时间的常听）；或
- 回退策略：先用 `7day`，条数 < 20 时改用 `overall`，两者合并去重。
- 推荐简单方案：直接 `overall`，减少请求与不确定性。

## 2. 「网易没有这首歌」是误会

实测 wy 搜索 `新·与天齐 指尖笑`（limit 50）第 41 条：

```
2159489286 | 新·与天齐 | ['指尖笑'] | 139
```

网易云**有**这首歌（很可能是云盘/上传曲目，网页搜索里不显眼），匹配本身是正确的；严格的标题+艺人匹配没有错配。

## 3. 匹配到但播放失败

这类“云端/上传/VIP”曲目用 `stream.resolve` 解析时容易失败（无版权、无播放地址、需要登录等）。

### 修法

1. **播放失败后自动换源**（用户已确认要这个行为）：
   - 播放器上报失败时，带着该行的 `match_key` 和当前 `provider` 回调推荐模块；
   - 把当前源记为该曲目的“失败源”，状态回到 `matching`；
   - 匹配 worker 跳过失败源，用**下一个源**重新查询；
   - 命中 → 推送新事件，行更新为新源并可再次播放；
   - 全部源失败 → 标记「无匹配」，不再自动重试。
2. 可选（成本高、本期不做）：匹配前先 `stream.resolve` 探测可播性；因为会多一倍请求且可能触发限流。

## 4. 测试

**Go**

- `GetTopTrackRecommendations` 使用 `overall`（或回退策略）时返回 50 首；
- 播放失败回调把该曲目重新入队、跳过已失败源；
- 全部源失败标记 `no_source`；
- 现有匹配/事件测试保持通过。

**前端**

- 播放失败后行状态回到「匹配中」并自动换源；新源命中后按钮恢复；
- 最终失败显示「无匹配」。

## 5. 验收

- 自动：§4 全绿；
- 人工：
  1. 打开页面有几十首常听曲目；
  2. 点播失败的行会自动换源重试；
  3. 网易那条「新·与天齐」播放失败后能换到其它源（如果有）。

## 6. 风险

- `overall` 的数据比 7day 更“旧”，但更稳定；
- 换源重试会增加匹配请求（只对播放失败的行，数量有限）；
- 云盘曲目可能所有源都没有可播版本，最终只能显示「无匹配」。
