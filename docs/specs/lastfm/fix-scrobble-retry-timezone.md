# Bug：重新登录成功后，待补传的 scrobble 迟迟不上传

> 状态：待开工
> 现象：重新授权成功（日志 `authentication successful`），但本地 22 条待补传 scrobble 一直不提交，Last.fm 最近记录不更新

---

## 1. 证据

- 重新登录时间：22:41:07，登录成功；
- 本地队列：22 条，`attempts = 5–7`；
- `next_retry_at` 存的是 **UTC 带偏移**：

```
2026-11-14 20:39:28.7212296+00:00
```

- 当前本地时间 22:45（UTC 14:45），而该时间按 UTC 解释是**次日 04:39 本地** → 未到期；
- 登录成功后没有新的 flush 日志（失败/成功都没有）。

## 2. 根因

### 2.1 重试时间与比较的时区不一致

- 写入时用 UTC（`20:39:28+00:00`）；
- `Due` 查询是 `datetime(next_retry_at) <= datetime(?)`，`?` 由 Go 的 `time.Now()`（本地 +08:00）绑定；
- SQLite 的 `datetime()` 会把带偏移的时间换算成 UTC 后比较：
  - 存储值 → `20:39`（UTC）；
  - 本地 now `22:45+08:00` → `14:45`（UTC）；
  - `20:39 <= 14:45` 为假 → 不算到期，要等到本地 **04:39**。

### 2.2 登录成功后没有唤醒队列

`CompleteAuth` 保存 session 后没有调用 `wakeScrobbleQueue()`，要等下一个 5 分钟 tick；而 tick 又因 2.1 判定“未到期”，于是看起来完全停住。

### 2.3 重新授权后没有重置退避

旧记录的 `attempts` 与 `next_retry_at` 是旧 session 失败留下的；新 session 应该立即重试。

## 3. 修法

1. **统一时间基准**：
   - 推荐 `next_retry_at` 存 **Unix 秒**（与 `started_at` 一致），或用 `TEXT` 但读写都用 UTC；
   - `Due` 用同一个基准比较，禁止“存 UTC、比较本地”；
2. **登录成功后唤醒**：`CompleteAuth` 末尾 `wakeScrobbleQueue()`；
3. **重新授权时重置退避**：
   - 新 session 建立后，把 `attempts=0`、`next_retry_at=now`（只针对尚未超过保留期的行）；
   - 或由 flush 在检测到 session 变化时强制立即发送一次；
4. 清理逻辑（30 天保留）不受影响。

## 4. 测试

**Go**

- 存储/比较时区一致：`next_retry_at` 为 UTC、now 为本地时，仍能正确判定到期；
- 时区边界：UTC+8 下“已到期”与“未到期”各一例；
- `CompleteAuth` 后立即 flush（fake 断言被调用）；
- 重新授权后 `attempts` 重置、`next_retry_at <= now`；
- 迁移/兼容旧行（旧格式的 `+00:00` 文本也能被正确读取）。

**人工**

1. 断网产生几条待传 → 重连 → 1 分钟内 Last.fm 出现记录；
2. 换 session 后旧退避时间不影响新 session；
3. 跨天/时区变化后仍能正常补传。

## 5. 验收

- 自动：§4 全绿；
- 人工：§5 三条成立。

## 6. 风险

- 旧数据格式（带偏移文本）需要兼容读取；
- 重置退避不应突破 30 天保留/5000 条上限；
- 避免在登录回调线程里同步发送网络请求（只唤醒 worker）。
