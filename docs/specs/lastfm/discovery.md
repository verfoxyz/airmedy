# 任务：Last.fm 页新增「发现」列表（只推没听过的歌）

> 状态：✅ 已完成（`kind=discover`、ISO 周种子轮换、≤30 请求预算、本地/近期 scrobble/每艺人 2 首过滤、候选池持久化与加载更多、12h TTL 受自动刷新开关控制；行与「为你推荐」一致先入列表再后台匹配）
> 目的：解决“软件缺少新歌推荐”——现有常听/收藏/最近播放都是已知歌曲
> 关联：`recommendation-lists.md`（歌单卡片与持久化）、`single-request-top-tracks.md`（匹配队列）、`fix-card-play-all.md`、`media-request-state-machine.md`

---

## 1. 定位

新增一种卡片：**发现**（`kind = discover`）。

- 只包含**不在本地库、且近期没有 scrobble 过**的曲目；
- 通过 Last.fm 的相似关系 + 标签 + 榜单扩展得到；
- 复用现有五源匹配队列，只显示可播放的行；
- 支持「加载更多」；
- ListenBrainz 作为**后续插件**接入（本期不做，留接口位）。

## 2. 种子（每周轮换，避免重复）

| 来源 | 方法 | 数量 |
|---|---|---|
| 常听艺人 | `user.getTopArtists`（`overall` 与 `6month` 每周轮换） | 前 10 |
| 常听曲目 | `user.getTopTracks`（`overall`） | 前 10 |

- 种子列表按周（ISO 周）缓存，同一周内结果稳定；
- 两个来源的种子合并去重。

## 3. 扩展（新歌来源，按优先级）

1. `track.getSimilar`（每个曲目种子，limit 10）；
2. `artist.getSimilar`（每个艺人种子，limit 5）→ `artist.getTopTracks`（limit 5）；
3. 种子艺人的 `artist.getTopTags` 聚合 → `tag.getTopTracks`（前 5 个标签，各 10 首）；
4. 仍不足时：`chart.getTopTracks`（20 首）兜底。

- 全部结果合并、去重（`title + ArtistSetKey`）；
- 请求预算：单次构建 ≤ 30 次 Last.fm 请求，超出即停止扩展；
- 单条失败只跳过。

## 4. 新颖性过滤

- **排除本地库已有**（标题 + 艺人集合匹配，与本地优先规则一致）；
- **排除近期 scrobble**：`user.getRecentTracks` 拉取最近 30 天（分页，最多 500 条）建立排除集合；失败则只排除最近 200 条；
- 排除种子本身；
- 同一艺人最多 **2 首**，保证多样性；
- 结果上限 100 条（可「加载更多」追加）。

## 5. 排序

```
score = 相似度权重 + 热度(log listeners/playcount) - 重复惩罚
```

- 相似度：来自 `track.getSimilar` 的 match 值，或“命中种子数”；
- 热度：`listeners` / `playcount` 取 log 归一化；
- 同分时按艺人名稳定排序，保证加载更多顺序一致。

## 6. 匹配与「加载更多」

- 复用现有五源匹配队列；只有匹配成功的行进入列表（与「为你推荐」一致）；
- **加载更多**：
  - 列表持久化时保留 `position` 与“未展开的候选池”；
  - 每次点击追加 20 条：从未匹配候选池继续匹配，完成后追加到列表尾部；
  - 候选池耗尽时，触发一次新的扩展（按 §3 顺序取下一页）；
  - 按钮在“匹配中/无更多”时置灰。

## 7. 持久化与刷新

- 复用 `lastfm_recommendation_lists` / `items`，`kind='discover'`；
- TTL：**12 小时**；打开页面超过 TTL 才重建；
- 页面右上角「自动刷新」开关控制是否检查 TTL；手动刷新始终可用；
- 匹配状态随行持久化。

## 8. 前端

- Last.fm 页卡片变为：**发现**、为你推荐、常听曲目（顺序：发现 → 为你推荐 → 常听）；
- 「发现」卡片样式与其它卡片一致（AlbumCard 风格）；
- 详情页（`/lastfm/lists/discover`）：
  - 与专辑详情一致（DetailHero + 搜索 + 悬浮栏）；
  - 列表底部「加载更多」按钮；
  - 行状态：匹配中 / 来自源 / 无匹配 / 已在库中（理论上不该出现，防御）。

## 9. 请求预算

| 阶段 | 请求数 |
|---|---|
| 种子 | 2 |
| 相似扩展 | ≤ 20 |
| 标签兜底 | ≤ 6 |
| 榜单兜底 | 1 |
| 最近 scrobble 排除 | 1–3（分页） |
| 合计 | **≤ 30 / 次重建** |

重建只在 TTL 过期或手动刷新时发生。

## 10. 测试

**Go**

- 种子合并去重、按周轮换（同一周稳定、跨周变化）；
- 扩展优先级与请求上限；
- 新颖性：本地已有被排除、近期 scrobble 被排除、每艺人 ≤2；
- 排序稳定性；
- 加载更多：追加 20 条、候选池耗尽后触发新扩展、无更多时置灰；
- 持久化：重启后内容与匹配状态不变；
- 部分失败只降级不失败。

**前端**

- 「发现」卡片与详情页渲染；
- 加载更多按钮状态与追加；
- 自动刷新开关控制 TTL 检查。

**人工**

1. 首次打开出现「发现」，内容多为没听过的歌；
2. 播放/保存正常；
3. 加载更多能追加新歌；
4. 一周后种子轮换，内容不再与上周完全相同。

## 11. 验收

- 自动：§10 全绿；
- 人工：§10 四条成立；
- 「发现」里不再出现本地已有的歌。

## 12. 后续（本期不做）

- **ListenBrainz 推荐插件**：提供真正的协同过滤推荐（`/1/recommendations`，需要用户 token）。接入方式为新的数据源插件，输出与 Last.fm 扩展相同的候选结构，直接进入本列表的候选池；本 spec 的过滤/匹配/加载更多逻辑复用。

## 13. 风险

- Last.fm 对冷门账号的相似数据仍可能稀疏，标签/榜单兜底保证有量但个性化下降；
- “近期没听过”只能用最近 30 天近似，更久之前的 scrobble 无法完全排除；
- 加载更多会带来新的匹配请求，需要共享匹配缓存并限并发。
