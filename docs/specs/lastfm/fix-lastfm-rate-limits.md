# Bug：Last.fm 请求被限流/连接被重置，导致只剩相似艺人

> 状态：待开工
> 现象：Last.fm 页顶部提示「部分请求失败，仅显示已返回的结果」，只有相似艺人，没有歌曲
> 关联：[fix-slow-matching.md](fix-slow-matching.md)（两段式返回已实现，本 bug 在更上游）

---

## 1. 现象与日志

应用日志：

```
WARN "failed to fetch lastfm user info" error="Get https://ws.audioscrobbler.com/2.0/?...user.getInfo...: EOF"
WARN "last.fm seed request failed" error="last.fm user.getLovedTracks: Get \"https://ws.audioscrobbler.com/2.0/?...\": EOF"
```

- 同样的接口用 `curl` / 简单 Go 程序直连是 200（网络可达）；
- 应用里出现 `EOF`（服务端在返回前关闭连接）→ 种子请求失败 → 四份列表没有候选；
- 相似艺人区块能显示，是因为它是另一条成功路径；
- 页面因此进入 partial 状态。

## 2. 根因

### 2.1 请求速率超过 Last.fm 限制

- Last.fm 官方限制约 **5 请求/秒/IP**；
- 当前客户端限流器是 **并发 3、间隔 250ms**（≈ 最高 12 req/s）；
- 打开一次推荐页会触发：3 个种子接口 + 每种子相似 + 相似艺人 + 兜底（标签/榜单），短时间几十个请求；
- Last.fm 对超速请求直接断开连接（表现为 `EOF`），不是总能返回 429。

### 2.2 没有重试

`EOF` 属于可重试的网络错误，但客户端一次失败就放弃；种子失败后不再重试，页面直接空。

### 2.3 缓存粒度

种子结果没有缓存，每次进页面都重新拉；配合上面的速率更容易触发限流。

## 3. 修法

### 3.1 限流降到官方范围内

- 并发 **3 → 2**；
- 最小间隔 **250ms → 400ms**（≈ 5 req/s 上限）；
- 所有 Last.fm 请求（种子/相似/标签/榜单/头像）共用同一个 limiter。

### 3.2 重试

- 对 `EOF`、连接重置、超时、5xx 做**最多 2 次重试**，指数退避（500ms、1500ms）；
- 429 时按 `Retry-After`（若存在）或固定 5s 等待一次；
- 重试仍失败才计为 partial。

### 3.3 种子缓存

- 三路种子结果缓存 **10 分钟**（按 username + 来源）；
- 页面刷新/重进优先用缓存，减少重复请求；
- 手动「强制刷新」跳过缓存。

### 3.4 部分失败时的 UI

- 只要有一份列表有数据，就正常显示（不要因为某个种子失败把四份都标成空）；
- 顶部提示改为「部分数据加载失败，稍后会自动重试」。

## 4. 测试

**Go**

- 限流器：并发 ≤2、相邻请求间隔 ≥400ms（fake clock 断言）；
- `EOF` 触发重试，第二次成功则整体成功；
- 重试耗尽后返回错误（页面 partial）；
- 429 时按预期等待再试；
- 种子缓存命中不重复请求；`force` 跳过缓存。

**人工**

1. 断网再恢复 → 打开页面不再出现大片 EOF 失败；
2. 连续刷新 5 次页面，最后一次仍能出歌（限流 + 缓存生效）；
3. 日志中不再频繁出现 `EOF` 警告。

## 5. 验收

- 自动：§4 全绿；
- 人工：§4 三条成立；
- 推荐页在正常网络下稳定出歌，不再长期只有相似艺人。

## 6. 风险

- 降低并发会让首屏变慢（种子 3 个接口串行约 1.2s），可接受；
- 重试可能放大请求量，需与限流器共用，避免重试风暴；
- 如果 Last.fm 对本机 IP 已临时封禁，需要等一段时间（几分钟到几小时）才能恢复，这属于外部状态。
