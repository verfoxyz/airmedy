# 需求：搜索候选（联想词与结果预览）

> 状态：待开工（范围：**本地候选 + 云端结果预览**；平台联想词暂缓）
> 相关：[`search-cache-plan.md`](search-cache-plan.md)（会话内缓存）
> 硬约束：AI 不做图形化测试；交互由人工确认。

---

## 1. 三种"候选"，先分清

| 方案 | 输入时看到什么 | 数据来源 | 本轮 |
|---|---|---|---|
| **① 本地候选** | 库里已有的歌名 / 艺人 / 专辑 | Bleve / SQL 前缀查询，不联网 | ✅ 做 |
| **③ 结果预览** | 云端搜索结果的前 5 行（歌名 + 艺人 + 封面） | 复用 `catalog.search` 的轻量模式 | ✅ 做 |
| **② 平台联想词** | 平台返回的建议词（如"晴天 钢琴版"） | 新增 `catalog.suggest`，每源一个接口 | ⏸ 暂缓 |

**为什么先做 ①+③**：用户真正的痛点是"记不清歌名"，直接看到结果行比看到关键词更有用；
而 ② 要给五个平台各写一套接口，我们连聚合搜索都还没完成，维护面会翻倍。

## 2. 参考实现（`reference/any-listen-extension-online-metadata`）

五个源**都有** `tipSearch.ts`（20–40 行），证明 ② 可行，也暴露了成本：

| 源 | 接口 | 返回形态 | 备注 |
|---|---|---|---|
| wy | `music.163.com/weapi/search/suggest/web` | `"歌名 艺人"` 字符串 | **weapi 加密**，移植成本最高 |
| kg | `searchtip.kugou.com/getSearchTip?MusicTipCount=10&keyword=` | `HintInfo` 纯词语 | 只需 `Referer`，最简单 |
| kw | `tips.kuwo.cn/t.s?...&rformat=json` | `RELWORD` | 官方 `searchKey` 接口 403，已换用此接口 |
| tx | `c.y.qq.com/splcloud/fcgi-bin/smartbox_new.fcg?...` | `"歌名 歌手"` | 需要 Referer |
| mg | `app.u.n.f.migu.cn/.../tone_search_suggest` | 歌手名 + 歌名去重 | 需要特定头 |

它们的实现共同点：**返回 `string[]`、失败直接抛、没有防抖与缓存**——防抖是宿主的责任。

**结论**：若将来做 ②，从 **kg** 开始（无加密、结构最简单），跑通链路后再评估其它源。

## 3. 交互规格（三种方案共用）

| 项 | 规则 |
|---|---|
| 触发 | 输入变化 250ms 后；中文 ≥1 字、英文 ≥2 字母 |
| 取消 | 新输入到来时中止上一个请求（`AbortController` / 请求版本号），旧响应不得覆盖新结果 |
| 布局 | 下拉浮层，宽与输入框对齐；`glass` 只用于这一层（悬浮表面），内部行用常规 hover token |
| 键盘 | ↑/↓ 移动、Enter 选中、Esc 关闭；`role="combobox"`、`aria-expanded`、`aria-activedescendant` |
| 空输入 | 显示**最近搜索**（最多 8 条，只存文字，不存结果） |
| 点击 | 候选**词** → 填入输入框并立即搜索；预览**行** → 直接跳到该曲目（等价于在结果页点它） |
| 分组 | 依次为：最近搜索 → 本地曲目 → 云端预览，每组最多 3–5 条，组有标题 |
| 降级 | 云端失败只隐藏"云端预览"组，不弹错；本地为空也不影响云端组 |

## 4. 数据与契约

### 4.1 本地候选

复用现有搜索索引，但走**前缀查询、限制条数**，不要复用完整结果页：

- 结果只需要 `{ title, artists, kind }` 三类字段；
- 顺序：歌名前缀 > 艺人前缀 > 专辑名包含；
- 上限 5 条，**不查封面**（下拉里用占位图标即可）。

### 4.2 云端结果预览

给 `catalog.search` 增加一个轻量模式，避免每次输入都触发完整扇出：

```
请求追加：preview: true, limit: 5
行为差异：
  · 只查"当前选中的源"，全部源时只查第一个可用源
  · 跳过名次融合与可下载性判定
  · 不返回分页游标
```

**不要**用现有完整搜索做候选：那会扇出到所有源、做融合去重、逐行查库状态，单次几百毫秒。

### 4.3 （暂缓）平台联想词

如果将来要做，契约是：

```
catalog.suggest  →  { query }  →  { items: string[] }
```

插件侧每源一个实现，宿主侧统一防抖与去重；宿主必须限流（同一前缀 1 秒内不重复请求）。

## 6. 验收

**自动**

- 组件 spec：输入触发一次查询、快速连续输入只保留最后一次结果（旧响应被丢弃）；
- 组件 spec：↑/↓/Enter/Esc 行为、`aria-*` 属性正确；
- store 单测：最近搜索最多 8 条、去重、按时间倒序；
- 契约测试：`preview: true` 时只查一个源、条数 ≤5、不做可下载性判定。

**人工（由人做，AI 不做）**

1. 输入"晴"：下拉出现本地曲目（若库里有）与云端预览行，带封面缩略图；
2. 快速改输入：不会出现旧结果闪回；
3. 点候选词：输入框更新并开始正式搜索；
4. 点预览行：直接定位到该曲目；
5. Esc 关闭下拉，焦点留在输入框；
6. 光明/暗/黑三主题下浮层可读。

## 7. 风险

| 风险 | 应对 |
|---|---|
| 每次输入都打云端 → 被限流 | 250ms 防抖 + 最小长度 + 同一前缀节流 |
| 预览行与正式结果不一致（排序不同） | 预览只取前 5 条，明确标注"预览"，正式结果以回车后的页面为准 |
| 下拉遮挡内容/移动端体验差 | 移动端（如后续支持）复用同一组件但减少分组 |
| 与搜索缓存互相干扰 | 候选查询不进缓存；缓存只作用于正式搜索结果（见 search-cache-plan） |
