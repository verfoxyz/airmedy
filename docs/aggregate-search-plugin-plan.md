# 需求评估：把「网易云搜索」插件改成「聚合版」（wy/kg/tx/kw/mg）

> 状态：待决策
> 结论先说：**技术可行，但这不是改名，是重写。** 建议分阶段，先把 wy 跑稳再逐源加。
> 硬约束：AI 不做图形化测试；界面与搜索质量由人工确认。

---

## 1. 现状

`plugins/wy/`：

- 插件 id `wy`，显示名「网易云搜索」，能力 `catalog.search`，`providers: []`；
- 只实现一个源：`src/search.js`（306 行）+ `wrapper.js`（337 行，握手/describe/search/unload）；
- 命中后返回 `{ provider: "wy", external_id, title, artists, album, duration, cover_url }`。

现在的「一个插件一个源」是当初的决定（`plugins/wy/README.md` 里写明：加 kg/kw/mg/tx 应该是各自的插件）。
改成聚合版等于**推翻这条决定**，所以要先把代价说清楚。

---

## 2. 改名的实际含义

| 改法 | 代价 | 风险 |
|---|---|---|
| 只改 `name` 为「聚合版」 | 5 分钟 | **名不副实**：还是只有一个源，用户会以为能搜五个平台 |
| 保留 id `wy`，加四个源 | 中 | id 叫 wy 却搜五个平台，误导维护者；已启用状态能沿用 |
| 新建 id 如 `aggregate`，替换旧插件 | 大 | 旧插件的启用状态、KV 设置不会自动迁移；用户需要重新启用 |

**建议**：新插件用新 id（`aggregate`），旧 `wy` 保留一个版本周期并在 README 标注"将被替换"。
理由：id 是数据契约，改语义不改 id 是长期债。

---

## 3. 每加一个源要做什么

以 `reference/any-listen-extension-online-metadata`（Apache-2.0，只借鉴算法，代码需移植）为参照：

| 源 | 搜索接口 | 关键点 | 估时 |
|---|---|---|---|
| wy | `music.163.com/api/search/get` | 已有实现，可复用 | 已完成 |
| kg | `mobilecdn.kugou.com/api/v3/search/song` 等 | 需要签名参数、UA 伪装；字段名与 wy 完全不同 | 1–1.5 天 |
| kw | `search.kuwo.cn/r.s` | 返回非 JSON（`'` 包裹），需先修正格式 | 1 天 |
| tx | `c.y.qq.com/soso/fcgi-bin/search_for_qq_cp` | 需要 referer、分页字段不同 | 1–1.5 天 |
| mg | `app.c.n.f.migu.cn` | 需要特定请求头，字段嵌套深 | 1 天 |

合计 **4–5 天**（不含逐字歌词、封面接口）。之后每个平台接口变更都要跟着修。

---

## 4. 必须先解决的产品问题：搜得到 ≠ 下得动

搜索结果里的 `provider` 决定能不能下载，而**播放地址由 lx 插件（用户导入的源）提供**。

所以聚合搜索上线后会出现：用户搜 kg 的歌 → 有结果 → 点下载 → "没有可用的解析源"。
这不是 bug，是当前架构的必然结果。

**三个选项**

1. **结果按可用性置灰**（已有 `downloadable` 机制）：搜索照常返回，不可下载的行禁用并说明
   "需要安装支持 kg 的源"。成本 0，体验诚实。
2. 聚合插件自己声明 `providers: [kg, kw, tx, mg]` 并实现 `stream.resolve` —— 等于把播放地址逻辑
   也搬进聚合插件，和「地址归 lx」的现有边界冲突，**不建议**。
3. 只做能被解析的源（当前只有 wy），其余等有解析方案再加。

**建议 1**：先按可用性置灰，等 lx 侧确实覆盖了这些平台，再放开。

---

## 5. 「成熟」具体指什么

不追求"五个源都能用"，先做到这四条：

1. **时间轴校验**：`[mm:ss]` 不存在就当失败，不返回空歌词；
2. **重试**：429/503 退避，非 200 不静默；
3. **字段稳定**：五源统一映射到同一个 row 结构，缺字段给 `null` 而不是空串；
4. **单源失败不影响整体**：某个平台超时，其它源照常返回，响应里带 `failures`。

---

## 6. 分阶段

| 阶段 | 内容 | 估时 |
|---|---|---|
| P0 | 新建 `aggregate` 插件骨架：多源注册表、统一 row、失败聚合；只接 wy | 1 天 |
| P1 | 加 kg（含签名与 UA），并接可用性置灰 | 1.5 天 |
| P2 | 加 tx / kw / mg，每加一个跑一次真实接口回归 | 3 天 |
| P3 | 插件显示名改为「聚合搜索」、README/设置页说明、12 locale 无需动（插件文案自带） | 0.5 天 |

合计约 **6 天**。

---

## 7. 验收

- 五个源各自能返回结构化结果；单源超时不拖垮整页；
- 不可下载的源在结果行上明确置灰并说明原因；
- 插件停用后云端搜索恢复"未安装搜索源"的空态；
- 现有 wy 插件的启用状态不被破坏（或明确告知需要重新启用）。

---

## 8. 风险

| 风险 | 说明 |
|---|---|
| 维护面从 1 个平台变成 5 个 | 每个平台的接口都可能变，出问题要同时修 |
| 一个插件挂掉等于五个源全挂 | 这也是当初"一源一插件"的理由；进程崩溃会带走全部 |
| 商标/合规 | 聚合本身不侵权，但"把五家都抓一遍"更容易被平台盯上；插件不随仓库分发已降低风险 |
| 与 any-listen 代码相似度 | Apache-2.0 允许借鉴，但直接抄代码需要保留 NOTICE 与署名 |
