# 需求：搜索缓存 —— 输入没变时保持搜索结果

> 状态：待开工（范围已定：**只做会话内缓存**，见 §4）
> 硬约束：AI 不做图形化测试；交互由人工确认。
> 相关：搜索候选（联想词与结果预览）见 [`search-candidates-plan.md`](search-candidates-plan.md)。

---

## 1. 目标

用户没改搜索框内容时，**回到搜索页仍然看到上次的结果**，而不是被清空或重新请求一遍。

具体到三种动作：

| 动作 | 期望 |
|---|---|
| 切到别的页面再回来（Tab 切回 `/search`） | 结果原样在，不闪加载态 |
| 切「本地 / 云端」再切回来 | 各自的结果都保留，不丢 |
| 应用重启 | **不恢复**：结果和查询词都清空（范围决定，见 §4） |

---

## 2. 现状（已核对代码）

| 层 | 现状 |
|---|---|
| 本地搜索 `stores/search.ts` | `query` / `results` 存在 Pinia 内存里，**同一次运行内切页是保留的** |
| 页面回到可见 | `useLibrarySync` 会调 `store.refresh()`，**无条件重跑一次本地搜索** |
| 云端搜索 `stores/catalog.ts` | 每次进入页面会重新请求第一页；分页位置、已加载的行会丢 |
| 应用重启 | 两种模式都不恢复 |
| 输入框 | `inputValue` 初始化为 `store.query`，本身不会触发重搜 |

所以现在"没动"的情况下，**结果会被一次不必要的刷新覆盖**，云端还会重新加载。

---

## 3. 方案（建议）

### 3.1 会话内缓存（必须）

1. **输入未变就不请求**：进入 `/search` 时比较 `store.query` 与输入框值，相同且 `results` 非空 →
   直接渲染，不调 `search()`；
2. **库变更时才失效**：`useLibrarySync` 的刷新改为"标记为 stale"而不是立即重跑；
   真正重跑发生在用户切回页面时（已有逻辑）或点了刷新按钮；
3. **云端分页状态保留**：`rows`、`page`、`hasMore`、当前源选择都留在 store 里，
   回到页面直接恢复，不再从第 1 页重来；
4. **显式刷新**：输入框右侧给一个刷新按钮（复用现有 `IconButton`），让用户主动重查。

### 3.2 跨重启（可选，建议不做结果、只做查询）

- 把 `query`、`mode`（本地/云端）、当前源存进设置，重启后**恢复查询词**并自动搜一次；
- **不缓存结果本身**：搜索结果会过期，长期存盘还会带来合规与磁盘问题；
- 如果确实要"重启后连结果也在"，必须给一个 TTL（例如 30 分钟），并在设置里说明会占用空间。

---

## 4. 范围（已定）

**只做会话内缓存**：切页、切模式不丢结果，也不重复请求；**应用重启后清空**。

明确不做：

| 不做 | 原因 |
|---|---|
| 重启后恢复查询词 | 本次范围内不需要；若将来要，加一行持久化即可 |
| 结果持久化 / 带 TTL 的磁盘缓存 | 结果会过期，还要处理 TTL、磁盘占用与隐私，收益不匹配 |
| 跨设备同步搜索历史 | 与本次无关 |

---

## 5. 验收

**自动**

- store 单测：`query` 未变且 `results` 非空时，进入页面**不发起**搜索请求；
- store 单测：`query` 改变时正常请求；清空输入时结果清零；
- 云端 store：回到页面时 `rows`/`page`/`hasMore` 与离开时一致，不重新拉第一页。

**人工（由人做，AI 不做）**

1. 搜一个词 → 切到「专辑」→ 切回「搜索」：结果还在，没有加载态闪烁；
2. 切到「云端」搜一次 → 切回「本地」→ 再切回「云端」：云端的分页位置和已加载行都在；
3. 改一个字：正常重新搜索；
4. 点刷新按钮：重新请求一次。

---

## 6. 风险

| 风险 | 应对 |
|---|---|
| 结果变陈旧（库里新增了歌却看不到） | 库变更时打 stale 标记，回页面时静默重查一次；并提供刷新按钮 |
| 云端结果长期占用内存 | 只保留当前一页 + 已加载分页，切模式时按需丢弃最旧的 |
| 与 `useLibrarySync` 现有逻辑冲突 | 把"立即刷新"改成"标记失效"，这是行为改变，需要同步更新它的 spec |
